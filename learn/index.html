    Chapter 0

    Thinking Like the Machine

    A hands-on course in the skills a computer science degree drills without always naming them: keeping an accurate picture of what the computer does, debugging by testing "what if" worlds, and picking the data shape that makes a problem easy.

    The argument you read

    Joe Marshall's post Not Everyone Can Code says debugging is counterfactual reasoning. To find a bug you have to suppose something you believe is false ("this pointer is null, even though I checked it two lines ago") and work out how that world could exist. He maps it onto Judea Pearl's three levels of causal reasoning:

    Pearl's levelThe questionWhat it sounds like in code
    1. AssociationWhat is?"The total is wrong whenever the cart has a mug in it."
    2. InterventionWhat if I do X?"If I remove the mug, the total is right again."
    3. CounterfactualWhy did Y happen?"For the total to be NaN, some multiplication must have had a non-number in it. Which one, and how did it get there?"

    He argues that people who copy recipes, glue libraries together or prompt an LLM without simulating the system stay on levels 1 and 2, and that concurrency makes level 3 much harder, because you have to reason about orderings you have never seen happen.

    What the research adds

    The diagnosis is useful. The fatalism is less well supported. Some points from computing-education research:

    • The cited studies measured untrained reasoning. The 1970s work he cites (Dulit, Keating, Neimark) studied Piaget-style "formal operational" reasoning in people who had not been taught it. That tells you where people start, not where they can get to. (I could not check the exact percentages he quotes.)
    • Debugging improves when it is taught as a procedure. In a controlled study, students given explicit instruction in systematic debugging improved both their debugging performance and their confidence compared with a control group (Michaeli & Romeike, 2019). A 2021 study found few novices use the hypothesis-testing method on their own, which suggests the problem is that nobody teaches it.
    • Labelling the purpose of each step helps. Worked examples whose steps are labelled with their goal ("subgoal labels") lowered dropout and failure in an intro programming course (Margulieux, Morrison & Decker, 2020).
    • You need a model of the machine. Novices struggle when they don't know what the computer does with each line. Researchers call the simplified picture you need a "notional machine" (du Boulay; Sorva, 2013). Chapter 1 builds one.
    • Reading and writing code are separate skills. PRIMM (Sentance and colleagues) orders practice as Predict, Run, Investigate, Modify, Make. Parsons problems, where you put scrambled lines in order, let you practise structure with less load (Ericson and colleagues).

    The move this course is built on. Marshall himself says very few people can reason about concurrency "without the aid of formal models or pure architectural restraint." Experts don't hold every what-if in their head either. They push the what-ifs out into things they can look at: a trace, a log line, an assertion, a test, a data structure that can't represent a bad state. Those aids can be learned, and they are what this course teaches.

    How to use this

    • Predict before you run. Every code box has a Predict field. Type what you think will happen, then press Run. Being wrong is the useful part: it shows you exactly where your mental model differs from the machine.
    • Then modify. All code boxes are editable. Change one thing, predict again, run again.
    • Mark chapters done at the bottom of each one. Progress is saved in this browser only.
    • Examples are in JavaScript, because it runs right here in the page. Every idea carries over to Python, Java, C# and the rest; Chapter 3 gives the Python names too.

    Chapter 1

    The machine in your head

    You can't imagine a world where "this variable is null" unless you know how a variable gets its value in the first place. Debugging is a comparison: what you think the machine did versus what it did. If your picture of the machine is vague, there is nothing to compare against. So we start by making the picture exact.

    Rule 1: a name points at a value

    A variable is a name. It points at a value. Assignment (=) makes the name point somewhere new. It is not an equation, and it does not link two names forever. Numbers, strings and booleans are small and get copied. Arrays and objects live in a separate area (the heap), and the name holds an arrow to them.

    Rule 2: each function call gets a fresh set of names

    When a function is called, the machine opens a new frame: a private box of names for that call. Parameters get the values that were passed in. When the function returns, the frame is thrown away. This is why a variable from inside a function "doesn't exist" outside it.

    Beliefs that break programs

    These are the most common wrong models researchers find in learners. Each one produces bugs you can't find, because your simulation of the code agrees with the bug.

    Wrong beliefWhat the machine actually does
    b = a links b and a foreverFor numbers and strings, b gets a copy at that moment. For arrays and objects, both names share one thing until one of them is reassigned.
    const makes an object unchangeableconst stops the name from pointing elsewhere. The object itself can still change.
    {...obj} makes a full copyThe spread copies one level. Nested arrays and objects are still shared. Use structuredClone(obj) for a deep copy.
    Code runs in the order it's writtenInside one function, yes. Callbacks and anything after an await run later, when the machine gets to them. Chapter 7 is about this.
    A variable can hold "whatever the user typed"Input from a form, file, URL or API is always a string or raw JSON until you convert it. "2" + 2 is "22".
    If the program didn't crash, the value is fineJavaScript keeps going with undefined and NaN. The crash, if any, happens far from the cause.

    Habit to build: when you read code you didn't write, keep a scratch "names and heap" table on paper for the variables that matter. It feels slow for a week, then it becomes automatic.     Chapter 2

    Debugging as a procedure

    The "insulting falsehood" Marshall describes is easier to entertain once you see it is just a line on a list. You don't have to believe that the value is wrong. You only have to write it down as one possible world and then check it. That turns level 3 reasoning ("why?") into a series of level 2 experiments ("what if I look here?"), which anyone can run.

    The loop

    1. Observe. Write down the symptom exactly: the input, what you expected, what you got. Make it happen again on demand.
    2. List the worlds. Ask: "For this output to appear, what must be true?" Write every answer down, including the ones you're sure are false. Especially those.
    3. Predict. For each world: "If this were true, what would I see if I looked at X?" A hypothesis that predicts nothing is useless.
    4. Experiment. Pick the check that rules out the most worlds for the least effort. Log a value, run a smaller input, comment out a line.
    5. Conclude and record. Cross out the worlds the evidence killed. Keep a logbook: what you tried, what you saw, what it means. Repeat until one world is left.

    Andreas Zeller's Why Programs Fail calls this scientific debugging. The logbook matters because without it you forget what you already ruled out and start testing in circles.

    Search, don't stare: the wolf fence
    
  
    When a value goes wrong somewhere in a long chain of steps, don't read every step. Check the value in the middle. If it's already wrong, the bug is in the first half; if it's right, the second half. Each check throws away half of the program. Eight steps need at most three checks. The same idea at the level of history is git bisect, which finds the commit that broke something.

Click a probe to see the value at that point. Find the broken step in as few probes as you can.
    
    
    
    
    
      
      
      
      
    
    
    
    
  
    

  
    Tactics that make counterfactuals cheap
    
  
    
    
    
      
    TacticWhen to use it
    
      
        
    Read the whole error message and stack traceAlways first. The bottom frame that's in your code is usually where to look.
    
        
    Shrink the inputThe bug appears on big data. Cut it in half until it disappears; the last piece you removed holds the cause.
    
        
    Diff working against brokenOne case works and one doesn't (like the two carts). The difference between them is a short list of suspects.
    
        
    Log the type as well as the valueconsole.log(typeof x, x). "8" and 8 look the same in many places.
    
        
    Explain it out loud, line by line"Rubber duck" debugging. Saying each step forces you to simulate it instead of skimming.
    
        
    Use the debugger's breakpointsYou want to see many variables at one moment. Browser DevTools and VS Code both let you pause and look.
    
        
    Bisect historyIt worked last week. git bisect searches the commits between.
    
          
    
    
  
    
  
    
    
    Using an LLM without skipping level 3. Paste the symptom and your list of worlds, and ask for experiments that would tell them apart, not for a fix. When it proposes a fix, ask "which of my worlds does this assume, and what evidence shows that world is the real one?" If it can't answer, you haven't found the bug yet.
    
  
    
  

    



    
  
    Chapter 3
    
  
    Data shapes come first
    
  
    The bug lab ended in a data problem: one item had quantity where the code expected qty. That's typical. Most confusing code is confusing because the data is the wrong shape, and the code is working around it.
    
  
    "Show me your flowchart and conceal your tables, and I shall continue to be mystified. Show me your tables, and I won't usually need your flowchart; it'll be obvious."Fred Brooks, The Mythical Man-Month
    
  
    "Data dominates. If you've chosen the right data structures and organized things well, the algorithms will almost always be self-evident."Rob Pike, Notes on Programming in C
    
  
    How to Design Programs makes this a rule: write down what your data looks like before writing any function, because the shape of the data decides the shape of the code. A list leads to a loop. A tree leads to recursion. A choice between kinds leads to an if or switch with one branch per kind.
    

  
    Six questions to ask about any data
    
  
      
    
    1. Is it one thing with named parts? A user has a name, email and age. → Object / record
      2. 
    
    2. Is it a small, fixed group where position is the meaning? An (x, y) point, a (value, error) pair. → Tuple
      3. 
    
    3. Is it many things of the same kind, in an order? Messages in a chat. → Array / list
      4. 
    
    4. Will you look things up by a key? Find the user with ID 42. → Map / dictionary
      5. 
    
    5. Do you only care whether something is present, with no duplicates? Tags, visited pages. → Set
      6. 
    
    6. Does it have a structure of its own? Processed newest-first or oldest-first → stack or queue. Contains smaller versions of itself → tree. Arbitrary connections → graph.
      7.

    Try 1,000 items, then 1,000,000. The array's time grows with the size; the Set's barely moves. For a list of 20 things, use whatever reads best. The difference only starts to matter for large collections checked many times, such as inside a loop.
    
  
    

  
    Tuples, records and the key trap
    
  
    JavaScript has no real tuple type. People use a short array instead: [x, y], or const [count, setCount] = useState(0) in React. That's fine for two values whose meaning is obvious. Past two or three, or when the order could be confused, use an object with names. Map libraries disagree about whether a point is [lat, lng] (Leaflet) or [lng, lat] (GeoJSON), and that disagreement has put plenty of markers in the ocean. { lat, lng } can't be swapped by accident.
    
  
    In Python, tuples are immutable and can be dictionary keys, so visited[(2, 3)] = True works. JavaScript compares arrays by identity, not by contents. Predict this one carefully:
    
  
    
  
    A plain object is the right choice for a record: a fixed, known set of fields. Use a Map for a collection keyed by values you don't know in advance. Object keys are always turned into strings, which causes quiet collisions:
    
  
    

  
    Real data nests
    
  
    Real programs combine the shapes: a Map from ID to record, where each record holds an array, and so on. A common, useful pattern is grouping: a Map from a key to an array of everything with that key.
    
  
    
  
    When the same thing appears in several places (a user who wrote posts and comments), store it once in a Map by ID and refer to it by ID elsewhere. This is called normalizing, and it's what databases do. If the user's name is copied into every post, renaming the user means finding every copy. Miss one and the copies disagree.
    

  
    Build it: count words
    
  
    A Parsons problem. The lines of a working function are scrambled. Put them in order with the arrows, then check. Indentation is a clue.

      Chapter 6
      
  
      Techniques: when to use what
      
  
      Each technique here does the same job: it cuts down the number of worlds you have to imagine when something goes wrong. A pure function has one world per input. A state machine has only valid states. An assertion turns a "suppose this were false" into a line that checks.
      

  
      Loops and map / filter / reduce
      
  
      
    
      
      
      You want to…Use
      
      
        
      Turn each item into one new itemmap
      
        
      Keep some itemsfilter
      
        
      Combine everything into one value (sum, max, object)reduce, or a plain loop if reduce gets hard to read
      
        
      Find the first match, or ask "any?" / "all?"find, some, every; they stop early
      
        
      Stop partway, track several things at once, or squeeze out speedA plain for loop
      
            
    
      
  
      
  
      

  
      Lookup table instead of an if/else chain
      
  
      When a chain of ifs maps one value to another, it's data pretending to be code. Put it in an object or Map. Adding a country becomes a one-line data change, and "what happens for an unknown country?" gets one clear answer instead of falling off the end of the chain.
      
  
      

  
      Guard clauses
      
  
      Handle the bad cases first and return early. The main path then reads straight down, with no nesting, and each early return is one world you've dealt with and can stop thinking about.
      
  
      

  
      Pure functions and side effects
      
  
      A pure function's result depends only on its arguments, and it changes nothing outside itself. That makes it the easiest code to debug: run it with the failing input and you've reproduced the bug. A function that reads a global or mutates its input has a hidden extra input, which is the whole world. Keep the logic pure and push reading files, network calls and DOM updates to the edges. People call this "functional core, imperative shell."
      
  
      

  
      Make impossible states impossible
      
  
      A loading screen tracked with three booleans has 2 × 2 × 2 = 8 combinations. Only four make sense. The other four are bugs waiting for a code path to produce them. Toggle the flags and see.
      
  
      
    
      
      
      
        
      Three booleans
      
        
      
          
          
          
        
      
        
      
      
      
      
      
        
      What the screen shows
      
        
      
      
      
    
      
    
      
      
      
    
      
  
      
  
      Replace the flags with one status field that can only hold the states that exist. Data that belongs to a state lives inside it, so you can't have an error message without an error.
      
  
      // 4 states, all of them valid
{ status: "idle" }
{ status: "loading" }
{ status: "error",   message: "Network down" }
{ status: "success", data: [/* … */] }

switch (state.status) {
  case "idle":    return showSearchBox();
  case "loading": return showSpinner();
  case "error":   return showError(state.message);
  case "success": return showResults(state.data);
}
      
  
      This is a small state machine. Reach for one whenever you catch yourself adding a boolean to describe what phase something is in: forms, uploads, checkouts, connections, game rounds.
      

  
      Assertions and checking at the boundary
      
  
      An assertion is a counterfactual written as code: "suppose this weren't true; stop right here and say so." It moves the crash from three functions later to the exact place the assumption broke.
      
  
      
  
      The best place to check is where data enters your program: a form, an API response, a file. Convert it there into the shape the rest of the code expects, once. After that boundary, the inside of your program can trust its data. (In TypeScript, the same idea is "parse, don't validate," and libraries like Zod do it for you.)
      
  
      

  
      Recursion for data that contains itself
      
  
      Use recursion when the data is a tree: folders in folders, comments with replies, nested menus, JSON. The function handles one node and calls itself for the children. For a flat list, use a loop.
      
  
      

  
      Tests: counterfactuals you keep
      
  
      A test is a what-if you write down once and the computer checks forever. When choosing test inputs, run through this list. Each line is a world your code might meet:
      
  
        
    
      • Empty: no items, empty string, zero
        • 
    
      • One: a single item; loops with one pass hide off-by-one errors
        • 
    
      • Many and duplicates: the same item twice
        • 
    
      • Missing or misspelled fields: quantity instead of qty
        • 
    
      • Wrong type: "8" instead of 8, null
        • 
    
      • Boundaries: exactly 3 items when the discount starts at 3; negative numbers; very large numbers
        • 
    
      • Text: spaces at the ends, capital letters, accents and emoji ("İzmir".toLowerCase() is a classic)
        • 
  
      

  
      Architecture in five decisions
      
  
      
    
      
      
      DecisionRule of thumb
      
      
        
      Where does this piece of state live?One owner. Everyone else asks the owner or gets a copy. Two places holding "the" cart will disagree.
      
        
      Should I make this reusable?Write it plainly the first time and copy it the second. Extract a shared function the third time, when you can see what actually varies.
      
        
      Class or plain object and functions?Plain data plus functions by default. A class earns its place when it guards a rule about its own data, like a bank account that never goes negative.
      
        
      Inheritance or composition?Prefer composition: build things out of smaller parts you pass in. Deep inheritance chains make "which method runs?" a hard question.
      
        
      How do I split the code into files?By what changes together. UI, business rules and data access change for different reasons, so keep them apart.
      
            
    
      
  
      
  

      



      
  
      Chapter 7
      
  
      Concurrency: debugging many histories
      
  
      Marshall calls concurrent code "counterfactual reasoning on steroids": instead of one history, there are many possible orderings, and the bug may live in one you've never seen. JavaScript runs one piece of code at a time, but it's still exposed: every await, timer and event is a point where other code can run and change the world before you continue.
      

  
      The lost update
      
  
      Two tasks each add €10 to a balance of €100. Each one reads the balance, adds 10 to its own copy, then writes the copy back. You choose the order the steps run in. Can you get €120? Can you get something else?
      
  
      
    
      
      
      
      
      
      
      
        
      shared balance
      
        
      €100
      
        
      Expected when both finish: €120
      
      
      
    
      
    
      Order so far: (none)
      
    
      
      
      
      
    
      
    
      
  
      
  
      That's the multiverse: twenty possible histories, and testing will mostly show you the lucky ones. Nobody checks all of them in their head. The practical answer is the "architectural restraint" from the article: design so that the dangerous orderings can't happen.
      

  
      The same bug in a search box
      
  
      A user types "ca", then "cat". Two requests go out. The first is slow; the second is fast. The answers come back in the wrong order.
      
  
      
  
      The fix: remember which request is the latest and ignore any answer that isn't. (In real code, AbortController can also cancel the old request.)
      
  
      

  
      Restraint that removes orderings
      
  
      
    
      
      
      TechniqueWhat it rules out
      
      
        
      Don't share changeable stateGive each piece of state one owner. Other tasks send it messages or requests instead of writing to it.
      
        
      Immutable dataIf nothing can change a value after it's made, nobody can see it half-changed.
      
        
      QueuesWork goes into a queue and one worker takes it out in order. Many writers, one sequence.
      
        
      Atomic operations and transactionsRead-change-write happens as one step. In SQL: UPDATE accounts SET balance = balance + 10 instead of reading in app code and writing back.
      
        
      LocksOnly one task at a time in a section. Effective but easy to get wrong (deadlocks), so prefer the options above.
      
        
      Idempotent operationsDoing it twice has the same effect as once ("set status to paid" rather than "add a payment"), so retries and duplicates are harmless.

        • Before running any code you just wrote, say what it will print. Every surprise is a lesson about your model.
          •
